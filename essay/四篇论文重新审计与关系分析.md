# 3. Learning Speed 旧笔记审计

## 3.1 总评

```text
Learning Speed
原笔记：正确 / 有少量需收紧表述
核心结论：经原论文复核，没有发现算法名称、RL action、sensor、EGO 角色、网络类型或主要数字的明显错误。
```

以下内容经原论文复核没有发现明显问题：

- 使用 SAC + PER；
- RL 输出动态速度约束 `v_t^†`，不是实际速度、局部目标或低层控制；
- EGO-Planner 仍负责内层轨迹生成；
- observation 含轨迹条件化地图、当前速度、跟踪误差、上一速度约束；
- 地图状态为 free、occupied、unknown、on_trajectory；
- 深度相机 15 Hz、策略 10 Hz、PID 50 Hz；
- 两阶段奖励、第二阶段冻结 CNN encoder；
- 30 个并行训练环境；
- RealSense D430、Jetson Orin NX、室内 NOKOV、室外 VIO；
- Figure 6、7 的读图数字已明确标成近似；
- 旧笔记已经正确质疑“formal safety guarantee”、EVA 比较完整性和真实实验统计不足。

## 3.2 问题 1：直接进入网络的并不是完整 3D map

```text
原笔记怎么写
“输入：当前 3D 局部占据地图 m_t……”；总览中也容易让读者理解为整张 3D map 直接进入 CNN。
↓
原论文实际是什么
3D local occupancy map 是构造观测的来源；作者把预规划轨迹画入地图后，沿轨迹按 δt 采样，只保留采样点对应的 x-y 2D cuts，再把这些切片输入网络。（PDF 第 4 页，Sec. V-B）
↓
为什么原笔记不准确/遗漏
旧笔记后文其实已经正确解释“沿轨迹抽取二维切片”，所以不是知识错误；但开头的简写若单独引用，会把网络输入维度和计算量说大。
↓
应该如何修改
统一改成：“观测来源是 3D 局部 occupancy map；网络直接接收的是带 on_trajectory 标记、沿预规划轨迹采样的 x-y 2D cuts。”
```

## 3.3 问题 2：不要把 EGO 输出简称为必然“可执行/安全”

```text
原笔记怎么写
部分总览使用“EGO 输出可执行轨迹”“规划器负责安全、动力学”等便于教学的简称。
↓
原论文实际是什么
作者把模型规划器称为具有 formal safety guarantee/generalizability，但实机章节又明确指出 EGO 的惩罚式动力学约束在紧急情形可能牺牲 dynamical feasibility，导致计划轨迹难以跟踪并碰撞。（PDF 第 7 页）
↓
为什么原笔记不准确/遗漏
旧笔记在“作者声称但证据不充分”和限制中已经纠正了这一点；问题只在前文的无条件简称，容易被截取后误解为数学保证。
↓
应该如何修改
把“生成可执行/安全轨迹”改为“以碰撞、平滑和动力学代价为目标生成轨迹；通常可跟踪，但论文明确报告紧急情况下可能牺牲动力学可行性”。
```

## 3.4 问题 3：若说 unknown、预规划轨迹“是关键”，应注明没有逐组件消融

```text
原笔记怎么写
“预规划轨迹 + unknown 地图状态是感知感知行为的关键输入设计。”
↓
原论文实际是什么
作者给出结构动机和行为案例，但消融只比较 stage 1 only、stage 2 only、stage 1+2，没有分别去掉 unknown、on_trajectory、tracking error 或 PER。
↓
为什么原笔记不准确/遗漏
“关键”在设计机理上合理，却容易被读成“实验已经单变量证明关键”。旧笔记其他章节已承认缺少这类消融，但速记结论没有带限定。
↓
应该如何修改
写成：“unknown 与预规划轨迹是作者认为产生 perception-aware 行为的重要设计；论文没有逐组件消融，独立贡献尚未量化。”
```

## 3.5 对当前项目最重要的防误解结论

```text
环境/局部地图 + UAV 状态 + 预规划轨迹
→ SAC 外层策略
→ 动态最大速度约束 v_max
→ EGO-Planner
→ 轨迹
→ PID/飞控
```

Learning Speed 的 RL **不直接避障、不选择路径拓扑、不输出速度命令、不输出推力**。避障空间轨迹仍主要由 EGO 决定；RL 只是调规划器允许的激进程度。

```text
RLoPlanner
```

- Table II 的 s/ms 冲突、200/250 任务冲突、训练计数不一致已正确指出；
- 奖励距离项符号、熵温度、`v_lp` 来源等复现歧义已正确指出。


# 6. 四篇论文统一比较

| 论文 | Sensor/Input | RL Observation | RL Algorithm | RL Action | Planner | 最终控制输出 | 是否端到端 |
|---|---|---|---|---|---|---|---|
| Learning Speed Adaptation | 前视 depth camera；局部 3D occupancy map；状态估计 | 沿预规划轨迹采样的四状态 x-y map cuts + 当前速度 + 跟踪误差 + 上一 `v_max` | SAC + PER，两阶段训练 | 标量/高层速度约束 `v_t^†` | **EGO-Planner 保留** | EGO 轨迹，经 50 Hz PID/飞控执行 | 否；学习只调 planner 速度约束 |
| Flying on Point Clouds | **Livox Mid-360** 点云 + IMU + Fast-LIO | 3200 维 surrogate + 机体系速度 + 姿态 + 高度 + xy 目标方向 + 上一推力/体率 | PPO | 期望 collective thrust + 3 轴 bodyrates | **无显式 planner** | 4 维低层指令送 PX4，50 Hz | 是“观测→低层控制”意义的端到端；不是原始点云→电机纯端到端 |
| RLoPlanner | 25 ultrasonic rangefinders，或 RGB-D depth→VAE；目标/方向信息 | `o=[ϑ,φ,D,ξ]` 或 `[ϑ,φ,I,ξ]` + LSTM 历史 | RSPG：recurrent maximum-entropy soft policy gradient | 机体系六维局部目标 `[x,y,z,φ,θ,ψ]` | **带 `J_lp` 的 EGO-Planner** | planner 的平滑、避障、动力学局部轨迹/控制序列 | 否；RL 是高层 local-goal policy |
| RLPlanNav | RGB-D depth `84×84×1`→50 维 VAE；目标/自身信息 | 显式式为 `[ϑ,φ,I,ξ]` + LSTM 历史；速度/角速度是否显式输入有原文歧义 | RDPG：recurrent deterministic policy gradient | 机体系六维局部目标 `[x,y,z,φ,θ,ψ]` | **EGO-Planner 保留** | planner 的 B-spline 局部轨迹/控制序列 | 否；RL 是高层 LoGP |

# 7. 四篇论文中“RL 学的东西”到底有什么不同

## 7.1 Learning Speed：学 aggressiveness

它学的是：“在当前可见环境、预规划路线和系统跟踪能力下，EGO 现在允许多快？”

- 改变时间尺度/速度边界；
- 不主动决定绕障拓扑；
- 不直接决定下一空间目标；
- 保留 EGO 的几何轨迹生成。

## 7.2 Flying：学 sensorimotor obstacle-avoidance control

它学的是：“看到这些方向距离、unknown、速度和目标方向后，下一 20 ms 应给多少推力和体率？”

- 同时隐式完成趋向目标、避障、速度行为和机动控制；
- 没有显式未来轨迹；
- action 权限最高，sim-to-real 与安全风险也最大。

## 7.3 RLoPlanner：学带探索性的 local-goal selection

它学的是：“根据有限视野与历史，下一段让 EGO 去哪个局部位姿，才能脱困并最终接近全局目标？”

- 最大熵鼓励探索多个可能方向；
- LSTM 记忆历史；
- EGO 负责怎样平滑到达；
- `J_lp` 强化高层局部目标对低层轨迹末端的约束。

## 7.4 RLPlanNav：学确定性的 local-goal selection

它也学“下一局部位姿”，但用 recurrent deterministic policy gradient：

- 核心是 LSTM 历史 + 确定性连续动作；
- 没有 RLoPlanner 的最大熵推导；
- 本文 EGO 目标只列平滑、碰撞、动力学三项。

## 7.5 一句话对照

```text
Learning Speed：学“多快”
Flying：学“下一瞬间怎么操纵”
RLoPlanner：学“下一段去哪”，并显式鼓励随机探索
RLPlanNav：学“下一段去哪”，使用循环确定性策略
```

# 8. 对 AstraDroneOpen 当前目标的价值

当前目标是：

```text
Mid360 + FAST-LIO + EGO-Planner + 绕塔
             + RL 动态调节 EGO 最大速度
```

因此本项目与 Learning Speed 的**控制架构**最接近，与 Flying 的**LiDAR observation representation**最接近。最合理的研究方向不是照搬 Flying 的推力/体率策略，而是研究能否把其 surrogate 作为 Learning Speed 外层速度策略的环境编码器。

以下部分均为“针对项目的工程推断”，不是四篇论文已经验证的组合。

# 9. Flying 中最值得借鉴到 Learning Speed 的部分

## 9.1 值得借鉴 1：历史点云统一到当前 body frame

对绕塔尤其重要：无人机持续转弯，若不做位姿补偿，多帧塔架会出现重影。项目已有 FAST-LIO odometry，可提供历史帧相对变换；但必须先锁定 `map/camera_init/body`、时间戳与 Mid-360 外参契约。

论文依据：Flying PDF 第 3 页明确使用局部状态估计，把 k 帧历史点云变换到当前 body frame。

## 9.2 值得借鉴 2：固定 3200 维方向—最近距离表示

它把不定长点云转为 MLP 可处理的固定向量，避免完整 3D occupancy CNN 的维度和 raycasting 开销。对塔腿、拉线、细杆比粗随机点采样更有希望。

限制：4.5°、3200 维和 10 m 截断来自 Flying 的低层控制任务，不能未经验证直接作为本项目最终参数。

## 9.3 值得借鉴 3：用历史 FoV 区分 point-free 与 unknown

这是比普通 range image 更重要的一点。绕塔时，塔体遮挡后方区域；“没有回波”不能自动解释为 free。`20-d_unknown` 给速度策略一个明确的谨慎信号。

限制：需要精确 Mid-360 FoV、历史位姿和 ray/FoV 几何；论文没有给完整构造算法。

## 9.4 值得借鉴 4：使用轻量 MLP encoder

Learning Speed 的目标动作只有一个速度约束，不需要把视觉网络做得和低层控制一样复杂。先把 surrogate 编成 environment feature，再与 tracking error、actual velocity、planner latency 和 preplanned trajectory 融合，符合低维高层动作的工程需求。

论文依据边界：Flying 证明了它在作者的 PPO 任务中比作者的 occupancy baselines 更易训练；没有证明它对 SAC `v_max` 策略同样优越。

## 9.5 值得借鉴 5：真实 LiDAR invalid return 是必须建模的风险

作者明确承认仿真没有模拟 Mid-360 的零半径 invalid observations 和材料反射率。这对铁塔金属杆、细线、斜入射和远距离回波尤其关键。这个负面结论本身比“细线成功案例”更值得项目吸收。

# 10. 三种方案比较

## 10.1 方案定义

### A：Learning Speed 原版

```text
Occupancy Map
→ 轨迹标记与 x-y cuts
→ CNN
→ RL
→ v_max
→ EGO
```

### B：参考 Flying

```text
Mid360 Point Cloud
→ 历史对齐 + point-cloud surrogate
→ MLP
→ RL
→ v_max
→ EGO
```

### C：融合方案

```text
Mid360 point-cloud surrogate
+ EGO preplanned trajectory
+ UAV/system state
→ fusion policy
→ v_max
→ EGO
```

这里的 UAV/system state 至少应考虑 Learning Speed 已用的 actual velocity、tracking error、上一 `v_max`；是否加入 planning latency/FAST-LIO confidence 属于项目设计，不是论文现成结论。

## 10.2 比较表

| 维度 | A Occupancy + CNN | B Surrogate + MLP | C Surrogate + trajectory + state |
|---|---|---|---|
| 信息完整度 | 局部体素拓扑较完整；沿轨迹 cuts 后聚焦相关区域 | 每方向只留最近表面/unknown 边界，拓扑和多层表面损失较大 | 保留 B 的局部几何，并补回“将走哪里”和系统执行状态；仍不等于完整地图 |

| 论文依据 | Learning Speed 直接依据最强 | Flying 对 Mid360 surrogate 直接依据强，对“输出 v_max”依据弱 | 是跨论文组合，架构动机强，但没有一篇论文直接验证 |

# 11. 三个方案不能做的错误推论

1. 不能用 Flying Figure 4 直接宣布 B/C 优于 A。Flying 的 occupancy baseline 是完整 `50×50×15` map CNN，不是 Learning Speed 的 trajectory-conditioned cuts。
2. 不能把 Flying 的 3200、4.5°、10 m、`k=5` 当作绕塔最优超参数。它们只是在作者任务中使用。
3. 不能认为有 surrogate 后 EGO 就不需要地图。当前项目仍保留 EGO，EGO 的避障输入和 RL observation 可以是不同表示。
4. 不能把 point-free 当 free；必须使用 FoV/unknown 逻辑。
5. 不能因 Figure 6 的 10 mm wire 案例声称 Mid-360 对塔上所有细构件可靠。作者明确报告真实漏检。
6. 不能让速度策略输出覆盖 EGO/bridge 的既有安全门禁、控制权唯一性、跟踪误差 HOLD 或任务高度契约。

# 12. 推荐

## 12.1 论文角度的推荐顺序

**推荐 C 作为中期研究目标，A 作为必须保留的基准，B 作为表示消融。**

理由：

- 当前任务明确不删除 EGO，所以 Learning Speed 的“RL 只调 `v_max`”应保持不变；
- Flying 最有价值的是 Mid-360 surrogate，而不是其低层推力/体率 action；
- 绕塔安全速度不只由附近点云决定，还取决于 EGO 准备走哪条局部轨迹、当前跟踪误差和系统延迟；
- C 同时保留 LiDAR 几何、unknown、路线相关性和系统能力信息，因果上最接近“这一段 EGO 允许多快”；
- 但 C 是跨论文新组合，没有直接论文证据，必须以 A/B/C 严格消融验证，不能直接进入实机自动控制。

## 12.2 不建议直接照搬 Flying 的内容

- 不采用推力/体率作为本项目 RL action；
- 不删除 EGO trajectory generation/tracking；
- 不直接使用其 reward 或 PPO 配置训练 `v_max`；
- 不把 50 Hz 低层 policy 当作当前阶段目标；
- 不把其仿真成功率转移为绕塔安全承诺。

# 13. 正式训练 Learning Speed 前最应该完成什么

最优先不是选 SAC/PPO，也不是马上写网络，而是建立**可审计的固定速度能力曲线与同步 observation 数据集**：

```text
同一 worksite/tower 场景、同一 EGO/FAST-LIO/PX4 参数
→ 多个固定 v_max 档位
→ 记录成功、碰撞/急停、规划超时、跟踪误差、最小净空、实际速度
→ 同步记录 Mid360 原始/预处理点云、FAST-LIO pose、FoV、EGO preplanned trajectory
→ 明确 map/camera_init/body 与时间戳契约
```

原因：Learning Speed 的训练目标建立在“固定速度越高，系统成功率与失效模式如何变化”这条能力曲线上。若当前项目还没有在 `worksite.world` 绕塔中稳定、可重复地测出这条曲线，RL 就没有可信的客观目标，也无法判断 surrogate 是否提供了必要信息。

在不启动训练的前提下，建议依次完成：

1. **数据契约**：锁定 Mid-360 点云 frame、FAST-LIO odom、body 外参、时间同步、EGO 预规划轨迹和 tracking error 定义。
2. **固定速度 baseline**：从低速开始，分级得到速度—成功率—最小净空—规划延迟曲线。
3. **离线 surrogate 验证**：不用 RL，检查历史对齐、3200 bin、unknown 与真实塔杆/遮挡是否一致，统计细杆回波丢失。
4. **A/B/C 表示消融设计**：固定同一数据、同一动作 `v_max`、同一 EGO 和同一评估场景，只改变 observation encoder。
5. **仿真—实机差距清单**：至少覆盖 invalid range、反射率、点云时延、FAST-LIO 漂移、外参误差和 EGO 规划耗时；在当前只验收 Gazebo 的范围内，先建立可注入的仿真扰动与离线真实数据检查方案。

# 14. 最终结论

- 四篇原始 PDF 全部找到并已按原文复核。
- 三份旧笔记都没有核心架构错误；Learning Speed 需要收紧“完整 3D map 直接输入/规划器保证安全”等简写，RLoPlanner 需要补 continuous action–softmax、Actor/Critic 符号等复现歧义，RLPlanNav 需要显式报告 ESDF 与 observation 的原文内部矛盾。
- Flying 最值得借鉴的是：历史点云当前机体系对齐、固定方向—距离 surrogate、FoV-based unknown、轻量 MLP 编码、以及对真实 Mid-360 invalid return/sim-to-real 风险的明确警告。
- 对当前项目，推荐保留 Learning Speed 的 `RL → v_max → EGO` 架构，把 Flying surrogate 作为候选 observation，最终重点研究方案 C，而不是照搬低层端到端控制。
- 正式训练前最重要的是先完成固定速度能力曲线、同步数据契约和 surrogate 离线验证。
